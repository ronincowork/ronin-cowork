One Record, Two Showings

How the setup flow is built, drawn. One path: an agent installs cowork on the owner's own machine, the owner opens the URL and lands on the setup page, and their first session is born from the page. The spine is live; two seams are open, both stitches. Prose companion: docs/setup.md.

which install

One of two doors — this page is the box you already have

Everything below is the bring-your-own-box install: a home server, a laptop, a VM you rent — a machine you control and are simply pointing at. You already have an agent on that box; you hand it docs/install.md, four commands land the release, and the product takes over from the URL. A second door — we provision the machine for you — will be its own product and is not written here. Its one obligation to this architecture: end where door one begins, a box you control with cowork serving, so nothing below ever knows which door was used.

the spine

Every surface is a face over one record

Both sessions built to the same sentence — yours: “first-run and the Setup tab are different stages of the same information.” There is one assembled record (GET /api/settei), one door for every write (updateConfig()), and no new store. First load asks in order and ends; the ⚙ Setup tab shows current values and never ends. Neither surface stores anything of its own.

built & wired the record — the spine open seam — built on one side, unwired on the other
first load

Birth is a stamped fact, wired at both ends

Freshness is never inferred: a genuinely fresh install stamps setup.pending at its first operator boot, nothing can re-arm it over HTTP, and a box that predates the key has no setup section and stays quiet forever — absence means do-not-show. The client asks a cheap route on every load and takes a pending box straight to the setup page; Save clears the flag before the handoff, so a first session that fails to start cannot leave a box pending. ?setup remains the deliberate way back in.

the handoff

Setup stops surveying — a form collects, a session resolves

The newest element, and the right instinct: a form cannot settle whether a repo is already cloned, where “half-finished” points, or what the owner’s note implies — but Ronin is full of agents who can simply ask. So the page is complete about what is mechanical and honest about what is not: it saves the settings, then bundles everything unresolved into a packet — the owner’s name, the machine, the project and its root, their note verbatim (projNotes, a field with deliberately no route), and the list of what a form could not settle — and launches the first session on it, under a new catalog-row job, 新 Atarashi: ask rather than assume, touch nothing outside the project directory unannounced, finish and stop.

The gap is when. Today the packet launches at Save, immediately — which assumes a usable agent already exists. On the fresh box this page exists for, the CLI may be neither installed nor signed in at Save, and launching into an unauthenticated CLI is the documented danger: Codex draws › for both its trust row and its ready prompt, so a blindly-delivered brief can answer the trust dialog. The packet needs a place to wait, and a trigger that drops the session in once an agent is established.

open seams

Two stitches remain

S1The standing tab does not read the manifest

setup-fields.js exists precisely so two surfaces cannot drift, and its header says both read it. Only first load does. Drift has already begun: the session cap is a 5/10/15/20 picker at first load but a free number with “0 = no limit” in the tab, and Mika’s model is asked at first load then shown read-only in the tab — the “asked once, never editable again” wizard failure both plans call the design’s cardinal sin.

Atarashi’s own gate is already waiting on this. The stitch: settei.js renders its set rows from the manifest; measured rows stay hand-drawn, since a fact has nothing to ask.

S4The packet cannot wait for an agent

The handoff launches at Save. On a fresh box no agent may be installed or signed in yet, the brief risks being delivered into a trust dialog, and if the launch fails the packet — the owner’s own words included — is simply gone; the fallback line says “open one from ＋ New” but nothing carries the brief there. The stitch: give the packet a durable home and a trigger that drops the 新 Atarashi session in once an agent is established (R5 decides which home and which trigger).

for discussion

The rulings this page wants from you

R1

Is every asked field re-answerable in the standing tab?

Concretely: Mika’s model. It lands in agents.jobs, which the tab renders read-only with a pointer to 目 Koshi — which does not edit MikaAssist.

My lean: yes — asked once means editable forever; S1’s stitch is where it gets fixed for free.

R3

KEYSTORE leg 1 — logins, or keys?

The one open question that sizes everything else. “Choose model providers” — a third of the stated flow — is blocked on it, and the honest scope may be small: Ronin can open a pane and run each CLI’s own login, holding nothing; a store is needed only for key-only providers.

My lean: logins for what has logins, a scoped store only for what cannot — it is the only answer that cannot trip the silent-billing trap the house already documented.

R5

Where does the packet park, and what drops the session in?

Three honest shapes. (a) The boot shelf: the packet becomes a boot file the first session reads on spawn — the store built for exactly “what a new session reads before anything else,” but it has no UI and nothing today spawns from it. (b) The server holds a pending launch: Save stores the packet beside setup in the record’s machinery, and the same probe that answers “installed” learns to answer “signed in” and fires the launch when it flips. (c) Launch now, deliver on ready: the pane opens immediately, the CLI runs its own sign-in there (§8.3 — Ronin’s unique move), and the brief is submitted only when the six-part contract says the prompt is genuinely ready, never into a trust dialog.

My lean: (c) as the spine, (a) as the parking form — the pane is already the one place sign-in can happen, Ronin already owns ready-detection, and a packet written to the boot shelf survives a failed launch instead of vanishing with it. (b) builds a scheduler nobody else needs.
