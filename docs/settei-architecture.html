One Object, Three Views

SETTEI is the top: one object holding everything this install is. It is fed from below — typed by the owner, scanned off the machine and everything in it, read from other stores by reference, derived from all of it — and every surface anyone ever sees is a view: a query over the object plus some furniture. There is no setup flow. There is a view that happens to be full on day one.

the model

Fed from the left, viewed from the right

The one declaration behind all of it: every leaf is declared once — label, teaching, where it lands — and no view may know a leaf the declaration does not say; that is what makes three renderers of one schema safe. The declaration is the registry (src/settei-registry.ts, pure data), served with every answer as schema; the client-side field list is deleted, because the schema of the object is part of the object.

the views

Three queries, three audiences

the setup view

askable ∧ unanswered · ordered

Reader: a human meeting Ronin. Teaches before it asks; ends. Admission is the birth key — a fresh install stamps setup.pending, the client routes on it, Save dismisses it. Never inferred, never re-armed.

The payoff: when a future feature adds new askable leaves, this view has content again — onboarding for new features falls out for free.

built · firstrun.js

⚙ the standing view

everything · current · editable

Reader: the owner, any day. Typed leaves are fields, found leaves are facts, derived leaves are readouts — provenance decides the rendering, not per-view logic.

Rule made structural: asked once means editable here forever. No leaf the setup view asked may render read-only here.

the rules

What holds it together

  • Every leaf knows how it is known — typed, measured, or derived. That is what lets any view render any leaf without per-view knowledge: input, fact, or task.
  • Only the typed half persists. A stored measurement is a lie the moment the box changes; a stored derivation is a to-do list that rots. Both are computed on read, so they can never be stale and never need un-writing.
  • One object means one answer, not one file. ronin.json holds what the owner typed; the object is assembled per read. Writes touch named keys through one door and preserve what they never heard of.
  • Secrets appear as presence, never value — in the object itself, so every view inherits the safety without knowing it exists.
  • Settei references other stores, never owns them. Projects live in the catalogs store and render here with their health; the roots file stays hand-editable and this never becomes its second owner.
  • The required path needs no agent. Install is mechanical, the setup view is a form, Save is complete. The reading list exists for the day an agent does.
